# ADR-025: 言語切替（i18n）システム

- **決定日**: 2026-07-20
- **作成日**: 2026-07-23
- **ステータス**: 承認済み

## 背景・課題

CELDA 2026 での国際発表・査読者による試用を見据え、UI を日本語だけでなく英語でも
利用できるようにする必要があった。要件は以下の通り:

- ボタンラベル・タブ名・説明文・設定パネルなど UI 全体（約 46 項目）を対象にする
- タブラベル・説明文は `ViewSwitcher.register()` の引数として渡される動的な文字列であり、
  静的 HTML の `data-i18n` 属性方式だけではカバーできない
- 言語選択を `localStorage` に永続化し、リロード後も維持する
- エラーメッセージ（JSInterpreter 由来）・サンプルプログラム名は翻訳対象外とする
  （前者は追跡困難、後者は固有名詞的でコストに見合わない）
- ADR-006（外部可視化ライブラリを使用しない）と同じ精神で、i18n も外部ライブラリ
  （i18next 等）に依存せず自前実装とする

## 決定

### モジュール構成

`src/i18n.js` に以下を実装した。

```js
import { t, getLang, setLang } from './i18n.js';

t('btn-edit')      // 現在言語の文字列を返す（ja: '✏ 編集', en: '✏ Edit'）
getLang()          // 'ja' | 'en'
setLang('en')      // 言語変更 → localStorage 保存 → 'langchange' カスタムイベント発火
```

- `STRINGS = { ja: {...}, en: {...} }` という単純なオブジェクトで文字列を管理する
  （外部 i18n ライブラリ・ICU メッセージフォーマット等は不採用）
- `t(key)` は現在言語 → 英語 → キー自体、の順にフォールバックする
- `setLang()` は `document` に `langchange` カスタムイベントを発火し、
  各モジュールがこれを購読して自身を再描画する（Pub/Sub 的な疎結合）

### 2 種類のローカライズ方式

UI 要素の生成方法が「静的 HTML」と「JS が動的生成するラベル」の 2 系統に分かれるため、
方式も 2 つ用意した。

| 対象 | 方式 |
|------|------|
| 静的 HTML 要素（ボタン・見出し等） | `data-i18n="key"` 属性を付与し、`applyI18n()` が `textContent` を一括更新 |
| タブラベル・ビュー説明文（`ViewSwitcher.register()` の引数） | `{ ja: '...', en: '...' }` オブジェクトをそのまま渡し、`resolveStr(v, lang)` ヘルパーが現在言語のキーを解決 |

`resolveStr(v, lang)` は `v` が文字列ならそのまま返し、`{ja, en}` オブジェクトなら
`lang` キーを参照する（`view-switcher.js` 内のヘルパー）。この二重方式にした理由は、
`ViewSwitcher.register()` の呼び出し側（`app.js`）に `data-i18n` 属性という概念が
存在しない（DOM 要素ではなく文字列引数として渡している）ため。

### 言語変更フロー

```
EN ボタンクリック → setLang('en') → dispatchEvent('langchange')
→ applyI18n()        // [data-i18n] 要素を一括更新 + html[lang] 属性を更新
→ switcher.setLang()  // タブラベル・説明バーを再描画
```

### 永続化

`localStorage('jsv-lang')` に `'ja'` または `'en'` を保存。デフォルトは `'ja'`。

## 根拠

- **自前実装（外部ライブラリ不採用）**: 対象文字列が約 46 項目と小規模であり、
  i18next 等のフル機能（複数形処理・名前空間分割・非同期ロード等）は過剰。
  ADR-006 の「可視化に外部ライブラリを使わない」という方針と一貫させ、
  依存を増やさない判断をした
- **`{ja, en}` オブジェクト方式**: `data-i18n` 属性は DOM 要素にしか付けられないため、
  JS 側で動的生成される文字列（タブラベル等）には使えない。呼び出し元で
  `{ja: '...', en: '...'}` を直接書く方式にすることで、翻訳の対応関係が
  コード上で一目瞭然になり、キー管理の間接層（`t('tab-state')` のような）を省略できる
- **`langchange` カスタムイベント**: 各モジュール（`ViewSwitcher`・`app.js`・設定パネル等）が
  互いを直接参照せずに言語変更へ追従できるよう、DOM イベントによる疎結合を採用した
  （ADR-002 の「単一の真実の源」とは別の軸だが、同様に直接結合を避ける設計判断）
- **エラーメッセージ・サンプル名を翻訳対象外にした理由**: エラーメッセージは
  JSInterpreter 側の実装に依存し追跡コストが高い。サンプル名は固有名詞的で
  翻訳の教育的価値が低いため、優先度を下げた

## 結果・影響

- `localStorage` キー `jsv-lang` が確立された
- `ViewSwitcher.register()` の第 2・第 4 引数（label・description）は
  文字列または `{ja, en}` オブジェクトのどちらも受け付ける仕様になった
  （既存の 13 タブすべてに `{ja, en}` を付与済み）
- 新しいビューを追加する際は、タブラベル・説明文を `{ja, en}` 形式で書くことが
  実質的な規約になった（文字列のみだと英語モードでも日本語のまま表示される）
- 静的 HTML に文言を追加する際は `data-i18n` 属性を付け忘れると英語モードで
  日本語のまま残る点に注意が必要
