# ADR-001: オムニシェントデバッグモデル（全ステップ事前記録）

- **決定日**: 2026-05-25
- **作成日**: 2026-06-14
- **ステータス**: 承認済み

## 背景・課題

JavaScript プログラムの実行を可視化する際、「ステップ実行」には大きく 2 種類のアーキテクチャがある。

1. **オンデマンド実行型**: ステップを踏むたびにインタープリタを動かし、次の状態を取得する
2. **全ステップ事前記録型（オムニシェント）**: 実行開始時に全ステップを一括記録し、UI はその配列上をナビゲートするだけにする

前者は逆方向ステップ（undo）の実装が困難で、任意位置へのジャンプも O(n) になる。教育用ツールとして「任意の過去の瞬間に戻る」「スライダーでジャンプする」ことが必須要件であった。

## 決定

`JSDebugger` のコンストラクタ呼び出し時に全ステップを `trace[]` 配列に一括記録する。以降のステップ操作は `cursor` の移動（整数インデックスの更新）のみで行い、インタープリタの再実行は不要とする。

```js
const dbg = new JSDebugger(sourceCode, { maxSteps: 100_000 });
// → dbg.trace[] に全ステップが記録される（O(n)、1回限り）

// ステップ操作は配列ナビゲーション（O(1)）
dbg.cursor += 1;          // 式単位で次へ
dbg.humanStep();          // 意味単位で次へ（humanStep インデックスを探索）
```

## 根拠

- **逆方向ステップが自然に実現できる**: 配列の cursor を減らすだけ
- **任意位置ジャンプが O(1)**: スライダー操作が即座に反映される
- **TraceBuilder で事前集計が可能**: ヒートマップ・ライフタイム等の集計データを init 時に 1 回計算し、キャッシュする
- **デメリット（許容範囲）**: 起動時のスパイク（maxSteps=100,000 で数百ms）。教育用の小規模プログラムでは問題にならない

## 結果・影響

- `DebuggerAdapter` の `moveTo(cursor)` がコア操作として確立された
- `TraceBuilder` の全集計メソッドがキャッシュ付きで設計された
- maxSteps を超えるプログラムは途中で打ち切られる制限を受け入れた
